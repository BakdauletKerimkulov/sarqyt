# CLAUDE.md

Sarqyt — TGTG-style marketplace для surplus food в Казахстане. Flutter + Firebase, два entry point (client / business) в одном репозитории.

## Источники истины — читать перед любой задачей
- `spec-driven-rules.md` — структура папок, именование, статусы спеков. Обязательно.
- `ai_toolkit/` — конвенции стека (архитектура, стиль, Riverpod, GoRouter, Firebase). Обязательно, читать целиком перед написанием кода.
- `ai_docs/` — знания проекта (PROJECT.md, EXTERNAL_SERVICES.md); уроки прошлых задач — в `ai_docs/solutions/`.
- `ai_specs/` — спеки фич. Для фич использовать `/spec` → `/refine` → `/plan` → `/work`, для багов `/fix`, для уроков `/compound`.

## Жёсткие правила
- **Git**: не выполняй `git add`, `git commit`, `git push`, `git merge`, `git rebase`, `git stash` и любые другие git-команды без явного разрешения пользователя. Разрешены только: `git remote`, `git branch`, `git checkout`, `git switch`, `git status`, `git log`, `git diff`.
- Никогда не выполняй `git push --force` и не меняй удалённые ветки без явного запроса.
- Не меняй публичные API, маршруты, пути коллекций/документов Firestore, имена JSON-полей и security rules без явного запроса.
- Не делай нерелевантные рефакторинги: не форматируй, не переименовывай и не перестраивай несвязанный код.
- Для рискованных изменений в `auth`, платежах, правах доступа или модели данных сначала предложи варианты и компромиссы.
- Предпочитай обратную совместимость схемы; миграции должны быть явными и задокументированными.

## Процесс работы
- Делай небольшие, корректные изменения, которые компилируются; предпочитай маленькие, обозримые диффы.
- Перед правкой читай связанный код: usages, data flow, соседние слои.
- Если требования неясны, задай максимум 1–2 уточняющих вопроса.
- Выбор, влияющий на архитектуру, API, модель данных, routing или UX — назови варианты и trade-offs; локальный и безопасный — реши сам.
- Перед редактированием кода покажи, что и почему собираешься изменить, и только потом вноси патч.
- При `git commit` создавай отдельную ветку с осмысленным названием.
- После нетривиального изменения запусти релевантную проверку (обычно `flutter analyze`; при затронутых codegen-моделях/providers — build_runner). Проверка упала — задача не завершена.

## Команды
- `flutter pub get`
- `dart run build_runner build --delete-conflicting-outputs`
- `flutter analyze`
- `flutter test`

## Стандарты кода (дополнение к ai_toolkit/code-style.md)
- Ранние возвраты для валидации и ошибок; вложенность не глубже ~2 уровней; функции маленькие, где возможно — чистые.
- Не оставляй мёртвый код и неиспользуемые импорты.
- Переиспользуй существующие виджеты и утилиты; два виджета, отличающиеся только данными, — один виджет с параметрами.

## Специфика проекта (нет в ai_toolkit/)
- UI-state, который должен переживать refresh/deep link, кодируй в route/query params, а не в заголовках, индексах или временных строках.
- Не делай fan-out чтения Firestore в UI; выноси чтения в репозитории и сервисы.
- Исправимые пользователем ошибки показывай рядом с полем или на уровне страницы; валидируй на границе controller/service, не в виджетах.
- Не глотай исключения; логируй с контекстом.

## Формат ответа
- Сначала коротко: что проверишь или изменишь и почему. Без формального плана для простых локальных задач.
- При правках кода упоминай риски и как проверить результат.
